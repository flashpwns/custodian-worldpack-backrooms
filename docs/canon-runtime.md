# Canon runtime coverage

YB-29 applies a canon-first rule: supported canon defines distinctive people, institutions, places, phenomena, procedures, and historical texture. Procedural generation supplies variation inside those limits; pack-original material supplies only explicit, conservative connective tissue; player history supplies world-specific consequences.

The existing pipeline is: source registry → verified locator or extraction → normalized claim → canon status → simulation authority → scenario/runtime trace → observer-safe experience. `npm run canon-runtime-report` joins `canon/source-registry.json`, `canon/claims`, and `data/runtime-traceability.json` to show which admitted claims reach runtime and which remain unimplemented, reference-only, or prohibited.

Runtime coverage is audit metadata, not a new authority tier. `FULLY_EXPRESSED` means a traceable runtime item has a claim and a defined mode delivery path; `UNIMPLEMENTED` means the claim has no such path. Production material remains production-only unless a separately admitted finished-material claim supports runtime use. Community and wiki records remain discovery/reference aids and never gain authority merely by being indexed.

Canon gravity is reported as meaningful categories rather than a percentage: canon-supported distinctive runtime items, explicitly pack-original distinctive runtime items, generic procedural fill, and untraced distinctive runtime items. A generic procedural chair never substitutes for source-supported distinctive world identity. Runtime traceability and pack-original provenance remain developer/report-only metadata, never ordinary player UI.

Current Pass-1 audit result: the registered corpus has no admitted named-character claims. That is an explicit coverage gap for Pass 2, not permission to invent canon biographies or silently label generated characters as canon.
